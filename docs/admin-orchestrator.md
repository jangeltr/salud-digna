# Administración y el orquestador

La aplicación usa `POST /api/v1/auth/login` con cuentas `ADMIN`. El JWT vive en memoria hasta cerrar la aplicación, cerrar sesión o alcanzar su vencimiento. Para cambiar el origen de la API central, configura `NEXT_PUBLIC_GENERAL_API_ORIGIN` antes de compilar. Por defecto se usa `https://api.salud-digna.app` en producción y `http://127.0.0.1:3000` en desarrollo. Permite el origen exacto del frontend en `CORS_ORIGINS`. Fuera de loopback se requiere HTTPS para la API y el frontend debe servirse por HTTPS.

- Dashboard usa `GET /api/v1/admin/overview`. Pendientes corresponde a `openRequests`.
- Supervisión usa `GET /api/v1/admin/requests` con `page` y `status`. El detalle presenta los datos autorizados del listado. La API devuelve último canal, fechas, paso y estado, y aún carece de un campo de canal inicial.
- Patient Journey y Centro de Orquestación consultan explícitamente `GET /api/v1/admin/requests/:id/journey`. La API devuelve el historial autorizado para un trámite y registra `ADMIN_JOURNEY_VIEWED` en auditoría. La consulta conserva el estado de negocio. La vista muestra el rol registrado cuando la API lo incluye.
- Usuarios, roles y catálogos conservan sus interfaces secundarias. El alcance de este cambio es el monitoreo del orquestador.

Pendientes con API: métricas agregadas de canales participantes y eventos procesados con criterios acordados, canal inicial y detalle operativo independiente del listado, ingesta global con filtros y estados de procesamiento, errores/reintentos, directorio y estado de conectores, y lectura paginada de auditoría autorizada por rol. El historial por trámite carece de estado de procesamiento y de identificadores de actor por diseño.

## Orquestador omnicanal independiente

El contrato fuente está en `origin/main` (`ff989cc`), en `apps/orchestrator/docs/journey-queries.md`, `apps/orchestrator/docs/journey-writes.md` y `apps/orchestrator/README.md`. La sección del orquestador usa la ruta Next.js `POST /api/omnichannel`, con operaciones concretas y un único destino HTTPS fijo. No llama a la creación de trámites.

Configura `ADMIN_ORCHESTRATOR_API_KEY` solo en el servidor de admin, con scope `JOURNEYS_READ`. Configura `STAFF_FRONTEND_ORIGIN` con el origen HTTPS exacto de esta aplicación y `GENERAL_API_ORIGIN` con el origen HTTPS de la API general para verificar cada sesión con `GET /api/v1/auth/me`. El navegador usa `NEXT_PUBLIC_GENERAL_API_ORIGIN` para la API central. Esta variable pública contiene solo el origen. El JWT existente de ADMIN se conserva en memoria y se envía al servidor Next.js como Bearer. El servidor verifica el rol activo y comprueba el origen y tipo de contenido de cada petición. No concede acceso al trámite mediante el rol del operador.

El operador de demostración introduce por HTTPS el UUID y el permiso temporal específico del canal en un formulario. El permiso se envía una vez en el cuerpo, se limpia del formulario, nunca se devuelve y se conserva en memoria del servidor vinculado al hash del token y un identificador aleatorio de la instancia de inicio de sesión. El servidor lo transmite por `X-Journey-Grant`; el orquestador valida el alcance y vencimiento reales en cada operación. La ventana local tiene un tope de cinco minutos, termina como máximo al expirar el JWT verificado y no extiende la vigencia real y limita la capacidad a 256 sesiones por proceso. Usa una instancia de Next.js por canal para la demostración. Un reinicio o cambio de instancia pierde el acceso guardado. Al recibir el cierre de acceso o sesión, el servidor elimina el permiso y cancela el trabajo en curso local. El vencimiento hace lo mismo. Si el cierre no llega por una interrupción de red, sigue aplicando el límite temporal. Cancelar una petición local no revierte un evento que el orquestador ya haya persistido. Excluye cuerpos y encabezados sensibles de registros, trazas y monitoreo del proxy y de Next.js.

Patient Journey y Centro de Orquestación consultan resumen, contexto e historial paginado del trámite con el permiso de Administración. El servidor solo permite lecturas. Dashboard, Supervisión y Recorrido API general conservan las consultas a la API general y sus UUID no se transfieren al orquestador. Quedan pendientes las métricas globales, ingesta y salud de conectores.

Antes de una prueba controlada, confirma con el responsable que el despliegue de demostración autorizado corresponde al contrato versionado. El operador del backend aprovisiona un trámite sintético existente y permisos separados para cada canal. Los permisos de demostración no se comparten entre aplicaciones. La creación idempotente y los códigos de continuidad ya figuran en `origin/main`, pero estas pantallas usan el traspaso manual con permisos emitidos por un operador. La identidad maestra, la reconciliación después de expirar y las escrituras de citas centrales siguen fuera del flujo.

Para observar la demo, un operador autorizado aprovisiona un grant independiente `READ_JOURNEY` para el canal de Administración y el mismo UUID que recibió Call Center. La clave de Administración solo necesita `JOURNEYS_READ`. Patient Journey muestra ese UUID como folio, las referencias reales de estudio y clínica, la versión y la línea de tiempo por canal. La transición a Pendiente de confirmación aparece en el historial solo si la devuelve el orquestador. Dashboard y Supervisión mantienen su fuente en la API general.
