# Call Center y el orquestador

El asesor inicia sesión con `POST /api/v1/auth/login` como `ADVISOR`. El JWT vive en memoria hasta cerrar la aplicación, cerrar sesión o alcanzar su vencimiento. Para cambiar el origen de la API central, configura `NEXT_PUBLIC_GENERAL_API_ORIGIN` antes de compilar. Por defecto se usa `https://api.salud-digna.app` en producción y `http://127.0.0.1:3000` en desarrollo. Permite el origen exacto del frontend en `CORS_ORIGINS`. Fuera de loopback se requiere HTTPS para la API y el frontend debe servirse por HTTPS.

1. El paciente genera una referencia con `POST /api/v1/requests/:id/assistance-code`.
2. El asesor canjea con `POST /api/v1/call-center/claim` y recupera la atención mediante `GET /api/v1/call-center/requests/:id` y `GET /api/v1/requests/:id/journey`.
3. Al revisar la atención lista, confirma con `POST /api/v1/call-center/requests/:id/confirm` y el cuerpo `{version}`. Un 200 devuelve la cita aplicada o recuperada. El backend asigna los IDs de evento y persiste sus eventos en la misma transacción. Ante resultado incierto, el reintento conserva el ID y la versión originales. Con 409 la interfaz recarga el contexto para una nueva revisión.
4. La interfaz vuelve a consultar estado e historial. Una interrupción en esas lecturas puede dejar una cita confirmada con contexto pendiente de actualizar.

Pendientes con API: descubrimiento de atenciones autorizadas para el asesor (incluida recuperación de un canje cuya respuesta se perdió), verificación de identidad separada del permiso operativo, comandos de contexto/reanudación/notas/mensajes para `ADVISOR`, agenda y disponibilidad, y contrato de ingesta general con identificador externo, idempotencia, acuse y consulta del resultado de procesamiento.


El 200 de confirmación debe contener un `AppointmentDto` completo en estado `CONFIRMED` y con el mismo `requestId`. Un 2xx inesperado, JSON incompleto, interrupción o 5xx deja el resultado sin verificar. Se conserva la versión del intento en memoria durante el permiso. Tras perder acceso se limpian cita, contexto, historial y versión. El mensaje genérico de resultado carece de identificadores y datos del paciente. Para reconciliar tras el vencimiento, el backend debe ofrecer una consulta con autorización renovada que vincule el intento con su resultado.

El contexto y el historial se consultan por separado. Si falla el historial completo pero llega el contexto autorizado, la vista puede mostrar los eventos recientes incluidos en ese contexto. Un 401, 403 o 404 en cualquiera de las dos consultas invalida la vista de esa atención.

El 429 muestra un aviso genérico cuando el navegador no puede leer `Retry-After`. Si se necesita mostrar los segundos exactos, el backend puede incluir `Retry-After` entre sus encabezados expuestos por CORS.

## Orquestador omnicanal independiente

El contrato fuente está en `origin/main` (`ff989cc`), en `apps/orchestrator/docs/journey-queries.md`, `apps/orchestrator/docs/journey-writes.md` y `apps/orchestrator/README.md`. La sección del orquestador usa la ruta Next.js `POST /api/omnichannel`, con operaciones concretas y un único destino HTTPS fijo. No llama a la creación de trámites.

Configura `CALL_CENTER_ORCHESTRATOR_API_KEY` solo en el servidor de call-center, con scope `JOURNEYS_READ` y `EVENTS_PUBLISH` para publicar. Configura `STAFF_FRONTEND_ORIGIN` con el origen HTTPS exacto de esta aplicación y `GENERAL_API_ORIGIN` con el origen HTTPS de la API general para verificar cada sesión con `GET /api/v1/auth/me`. El navegador usa `NEXT_PUBLIC_GENERAL_API_ORIGIN` para la API central. Esta variable pública contiene solo el origen. El JWT existente de ADVISOR se conserva en memoria y se envía al servidor Next.js como Bearer. El servidor verifica el rol activo y comprueba el origen y tipo de contenido de cada petición. No concede acceso al trámite mediante el rol del operador.

El operador de demostración introduce por HTTPS el UUID y el permiso temporal específico del canal en un formulario. El permiso se envía una vez en el cuerpo, se limpia del formulario, nunca se devuelve y se conserva en memoria del servidor vinculado al hash del token y un identificador aleatorio de la instancia de inicio de sesión. El servidor lo transmite por `X-Journey-Grant`; el orquestador valida el alcance y vencimiento reales en cada operación. La ventana local tiene un tope de cinco minutos, termina como máximo al expirar el JWT verificado y no extiende la vigencia real y limita la capacidad a 256 sesiones por proceso. Usa una instancia de Next.js por canal para la demostración. Un reinicio o cambio de instancia pierde el acceso guardado. Al recibir el cierre de acceso o sesión, el servidor elimina el permiso y cancela el trabajo en curso local. El vencimiento hace lo mismo. Si el cierre no llega por una interrupción de red, sigue aplicando el límite temporal. Cancelar una petición local no revierte un evento que el orquestador ya haya persistido. Excluye cuerpos y encabezados sensibles de registros, trazas y monitoreo del proxy y de Next.js.

Call Center consulta resumen, contexto e historial paginado. Para publicar en `POST /events`, el backend genera un UUID de evento y conserva exactamente el cuerpo serializado, con `schemaVersion: 1` y `expectedVersion`. El botón de reintento solo identifica la acción original. Un 201 con recibo válido acredita persistencia por la semántica transaccional documentada. Un 409 se muestra como conflicto genérico y provoca una nueva lectura; el backend no distingue la causa en su respuesta HTTP. Una respuesta ambigua queda pendiente y puede reintentarse explícitamente dentro del mismo acceso. Un reinicio o vencimiento exige reconciliación mediante un permiso nuevo y revisión del contexto e historial antes de iniciar otro avance.

Antes de una prueba controlada, confirma con el responsable que el despliegue de demostración autorizado corresponde al contrato versionado. El operador del backend aprovisiona un trámite sintético existente y permisos separados para cada canal. Los permisos de demostración no se comparten entre aplicaciones. Como alternativa, la pantalla Continuar atención permite usar el código de un solo uso emitido por el canal anterior. La creación sigue a cargo del canal de origen. La identidad maestra, la reconciliación después de expirar y las escrituras de citas centrales siguen fuera del flujo.

### Continuar atención para la demo

El asesor ingresa el código de 12 caracteres en el formulario. El servidor revalida la sesión y canjea con `POST /api/v1/continuity-codes/redeem`, enviando solo `{code}` con la clave privada del canal. Valida el 201 y guarda el grant antes de responder con UUID y vencimiento local. El plazo es el menor entre el vencimiento del grant, el JWT y cinco minutos. Las lecturas se ejecutan en una petición posterior. Si fallan, se reintenta la lectura, y si se pierde la respuesta del canje se puede recuperar el acceso de la misma sesión sin reenviar el código. Si el servidor no conservó el grant, se necesita un código nuevo. No incluyas códigos o grants en registros, URLs o almacenamiento persistente.

El permiso del canje concede lectura y publicación según el contrato. El servidor consulta `GET /api/v1/channel-auth/verify` para comprobar ambos scopes de la clave antes de habilitar el avance. Antes de publicar un evento nuevo comprueba otra vez el scope, el estado `IN_PROGRESS`, ambas referencias y la versión. Un conflicto devuelve a la revisión. El resultado final se muestra cuando el resumen leído confirma `PENDING_CONFIRMATION`. El folio es el UUID y las referencias de estudio y clínica se muestran como UUID. Este avance no crea una cita en la API general.


## Continuidad institucional

Contrato revisado en `7df5c1b`. La API central emite el consentimiento únicamente a un backend con sesión PATIENT y su propia clave de canal. El cuerpo es `{advisorId, channel}`, donde el identificador es el UUID de la cuenta ADVISOR activa y el canal destinatario es `demo-callcenter`. El éxito es 200 con `{consent}`. El portal publicado en el repositorio todavía deja fuera la emisión para el asesor y su entrega entre backends. La documentación del emisor admite un medio administrativo privado para la demo.

Configura en el servidor de Call Center `CALL_CENTER_PATIENT_ASSERTION_CHANNEL_KEY` con la credencial de emisión central de `demo-callcenter`. Es independiente de `CALL_CENTER_ORCHESTRATOR_API_KEY`. Configura `CALL_CENTER_PATIENT_CONSENT_DIR` como ruta absoluta a un directorio privado **fuera del repositorio**, accesible solo al servicio y al operador autorizado que entrega el consentimiento. Usa un archivo de texto `<UUID de cuenta ADVISOR en minúsculas>.jws` por asesor, con el consentimiento central vigente y ningún otro dato. Sustituye el archivo de forma atómica cuando el paciente autorice otra atención, y retíralo al vencer o terminar la prueba. El JWS permanece entre backends y el navegador carece de campos para entregarlo.

**Comprobar autorización institucional** revalida la sesión ADVISOR y lee únicamente el archivo asociado a su identidad autenticada. Envía `{consent}` con su JWT y `X-Patient-Assertion-Channel-Key` a `POST /api/v1/auth/patient-assertions` sin reenviar Origin. La API central comprueba la firma, el canal, el asesor destinatario, la vigencia y que el paciente sigue activo. Ante 200, Call Center verifica la forma y duración de la acreditación para `demo-callcenter`. El orquestador verifica la firma al recibirla. La acreditación queda en memoria ligada a la sesión, durante un máximo de cinco minutos y nunca más allá del JWT ni del consentimiento.

`GET /api/v1/journeys?active=true` usa `X-Patient-Assertion` y la clave del orquestador con `JOURNEYS_READ`. Devuelve `{items}`, con hasta 100 trámites `DRAFT`, `IN_PROGRESS` o `PENDING_CONFIRMATION`. Cada elemento incluye `id`, `type`, `status`, `createdAt` y `updatedAt`. El canal de origen no forma parte de ese resumen. El servidor guarda únicamente los UUID autorizados para esa acreditación y reemplaza la lista al actualizarla.

El servidor solicita `POST /api/v1/journeys/:journeyId/access-grants` sin cuerpo y con esos mismos encabezados, únicamente para un UUID del listado. Valida el 201 con `journeyId`, `grant` y `grantExpiresAt`. El grant se custodia en memoria, ligado a la misma sesión y trámite. La respuesta al navegador solo entrega los datos del listado o el identificador seleccionado y su vencimiento. El acceso reutiliza las lecturas de resumen, contexto e historial. La publicación conserva los controles de `expectedVersion` e idempotencia. Requiere que la clave del orquestador tenga `EVENTS_PUBLISH`; tras aceptar el evento, la interfaz obtiene el estado vigente mediante una lectura.

Cuando vence el acceso o el orquestador rechaza su autorización, se limpia la atención en memoria. El asesor debe volver a comprobar un consentimiento vigente. El consentimiento se puede presentar otra vez hasta su vencimiento y el contrato no ofrece revocación anticipada individual. Cerrar la atención libera los datos en memoria de esta instancia. Los trámites provisionales o asociados a fixtures antiguos no se recuperan por esta ruta. Para la demo, crea el trámite sintético en Portal Web con la acreditación institucional y conserva la decisión del paciente al emitir el consentimiento. La alternativa por código sigue disponible.

### Custodia de archivos en Linux

Ejecuta Next.js desde el directorio de la aplicación o del worktree, con un usuario dedicado sin privilegios y con `salud-digna-callcenter` como grupo primario. El lector compara el GID numérico del archivo y del directorio con el GID primario del proceso y exige UID 0. Usa modo `0750` para el directorio y `0640` para cada archivo, sin ACL adicionales que amplíen el acceso. Los componentes superiores deben pertenecer a root y carecer de permisos de escritura para grupo u otros. La ruta debe quedar fuera del worktree y de las carpetas públicas de Next.js.

El lector exige Linux con `/proc/self/fd`. Abre cada componente mediante el descriptor del directorio anterior y comprueba los metadatos sobre los descriptores. En Windows o ante una ruta insegura, la verificación institucional por archivo se rechaza. Los códigos de continuidad siguen disponibles.

El operador autorizado retira el archivo. El servicio web carece de permiso para modificarlo o eliminarlo. La ausencia del archivo impide una nueva emisión. **Eliminar el archivo no revoca anticipadamente las acreditaciones ni los access-grants ya emitidos.** Estos permisos mantienen su caducidad o revocación contractual. La API central comprueba la caducidad del consentimiento al emitir la acreditación.
